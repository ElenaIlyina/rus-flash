# Обновление банка по выгрузке автора

Решение от **29.10.2026**: сайт доступен автору; у среды разработки остаётся
403 от прокси. Автор подготовила полный список шестизначных кодов и сырые
JSON заданий, сейчас проверяет принимаемые ответы подбором.

## Что принимаем

Файлы в уже имеющемся формате, без обязательного переименования или ручной
перекладки полей. Импорт адаптируется после просмотра реальной схемы.

1. Полный список кодов и сырые JSON — снимок содержимого банка на дату выгрузки.
2. Результаты проверки ответов — отдельно от исходника и редакторских разборов.
3. Для ответа важно знать код/GUID, отправленный ответ, принят ли он, дату
   проверки и версию задания, включая порядок вариантов. Если эти сведения уже
   есть в логе подбора, используются они; повторно проверять их вручную не нужно.

Успешный подбор подтверждает **принимаемый ответ**. Он не доказывает
единственность ответа и не восстанавливает весь скрытый перечень допустимых
вариантов сервера. Строки битмаски и перечень номеров нельзя смешивать:
`11101` и `1235` эквивалентны только при известных типе ответа и порядке вариантов.

## Порядок работы

### 1. Зафиксировать исходники и происхождение

Оригиналы сохраняются без изменения; фиксируются дата, источник, хеши файлов
и связь с кодом/GUID. Данные читаются как данные, без исполнения вложенного HTML.
Полные исходные снимки и логи относятся к `dev/`, готовые материалы приложения
публикуются отдельным этапом. Пользовательская сборка не получает зависимость
от журналов, тестов или инструмента импорта.

### 2. Составить отчёт расхождений

Сопоставление идёт по коду **и GUID**, а не по алфавитному месту карточки.
Сравниваются текст, условие, варианты, порядок, выделения, КЭС и формат ответа.
Отдельно показываются новые карточки, изменившиеся карточки и отсутствующие
в снимке ID. Отсутствие в списке не означает автоматического удаления из проекта.

Подготовленные объяснения, подсказки и словарные ссылки сохраняются при
сопоставлении. Содержательное изменение источника делает прежнюю редакторскую
сверку устаревшей: объяснение нужно заново проверить, а не переносить молча.
Сначала — приоритет №1–4; неподтверждённые исходники и ключи не додумываются.

### 3. Связать подтверждённые ответы с версиями

Ответ принимается как подтверждённый только для того текста и порядка
вариантов, на которых его проверяли. Словарно допустимый синоним без успешного
ответа сервера в перечень принимаемых не добавляется. Если сервер принимает
несколько ответов, это записывается как подтверждённая вариативность с
отдельными свидетельствами. Правила нормализации и оценивания меняются
осознанно, с проверкой совместимости; старые события не переписываются молча.

### 4. Согласовать реальные правки исходников

Условия, текст и варианты редактируются после согласования автора конкретного
отчёта различий. Уже разрешённое удаление точных дублей и согласованные
выделения повторного разрешения не требуют. Старые объяснения можно заменять
по действующему разрешению, сохраняя журнал причин и хешей.

### 5. Подготовить и проверить разборы

На актуальном исходнике проверяются смысл решения, каждый вариант, подсказка,
ссылка на конкретный источник, оценивание и отображение. Спорный ключ и
неполный источник учитываются раздельно: словарное сомнение не отключает
принятый сервером ответ и не разрешает произвольную замену задания.

Каждая партия сопровождается отчётом, тестами и самостоятельным коммитом.
В production нет редакторской очереди, исследовательских статусов и планов.

## Как ограничиваем нагрузку автора

Одна [очередь проверки вторых ответов](author-answer-checks.md), не несколько
параллельных списков. В активной партии максимум **три карточки**. Для каждой
даны конкретный ответ и причина, проверка не требует самостоятельного поиска
синонимов или разбора теории.

Перед выдачей очереди её сверяют с полным списком кодов и логом подбора:
уже проверенные варианты исключаются. Достаточно одного из результатов:
«принят», «не принят», «не нашла». Техническая ошибка/отсутствие карточки не
записывается как отрицательный результат проверки ответа.

Следующая партия выдаётся после завершения текущей. Все языковые сомнения
ассистент сначала исследует самостоятельно; автор получает только вопросы,
которые действительно может решить ответ сервера.

## Проверки не блокируют основную работу

Очередь вторых ответов и автоматическая проверка всего банка — параллельный
поток. Пока результата нет, действующие ключи сохраняются и продолжается
подготовка объяснений, подсказок, теории и источников. Ожидание ответа не
переводит весь раздел в состояние «остановлено».

По предложению автора вместо ручных запросов используется
`dev/scripts/check_fipi_answers.py`: явные кандидаты → `solve.php` → журнал
приёма/отказа/технической ошибки. Одна принятая строка не объявляется полным
перечнем допустимых ответов. [Запуск и паузы](fipi-answer-checks.md).

Получен образец `src.zip`: список 2140 кодов и **один** сырой JSON 005141,
как и предупредила автор. Формат `{number, guid, html}` принят без изменения.
Полный свежий набор карточек пока не получен; данные не подменены перечнем ID.
