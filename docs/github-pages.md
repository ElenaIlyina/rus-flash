# Ручная публикация через GitHub Actions и Pages

## Что подготовлено

`.github/workflows/deploy-pages.yml`: только workflow_dispatch. Push и Pull Request сами по себе не запускают публикацию. Один репозиторий Pages обслуживает один выбранный опубликованный сайт; это не автоматические отдельные preview-сайты для каждого PR.

Workflow:

1. Получает код выбранной при ручном запуске ветки/рефа.
2. Использует Python 3.12 и выполняет `bash scripts/install.sh`.
3. Создаёт JSON-каталог и отдельные JSON-карточки в html/assets/data/. Старые HTML-карточки не генерируются.
4. Копирует html/ в отдельный `_site/`, проверяет наличие модулей, импортируемых CSS и всех карточек.
5. Загружает Pages-артефакт и публикует его через отдельную задачу с environment github-pages.

Публикуется содержимое html/: текущая оболочка, стили, JS, логотип и сгенерированные данные. Старый интерфейс для сравнения удалён. Исходный data/, документация, Python-утилиты и тесты в артефакт не попадают. Все опубликованные данные доступны посетителям: ответы находятся в клиентских файлах по архитектуре тренажёра. Секреты, личная история и ключи в сборку не добавляются.

Actions закреплены полными SHA официальных репозиториев, токен checkout не сохраняется, сборка получает contents:read и pages:read; только deploy получает pages:write и id-token:write. Для публикации не нужен личный GitHub-токен или API-ключ модели. Два запуска не публикуются одновременно; текущая публикация не отменяется новым запуском.

## Однократная настройка владельцем

1. Проверьте и перенесите файл workflow в **основную ветку** репозитория. GitHub не показывает штатный ручной запуск нового workflow, пока он отсутствует в default branch. Можно перенести только инфраструктуру публикации; весь редизайн объединять заранее не обязательно. Но запускаемая ветка должна содержать сам workflow, scripts/install.sh и scripts/check_pages_artifact.py.
2. В Settings → Pages выберите Source: **GitHub Actions**. Настройки доступны владельцу/администратору; доступность Pages зависит от видимости репозитория и тарифа. Workflow не пытается автоматически создавать/менять Pages.
3. Проверьте ограничения Actions в Settings → Actions → General: официальные actions должны быть разрешены.
4. Если environment github-pages ограничивает ветки, разрешите **конкретную ветку**, из которой хотите публиковать (main либо feat/slovo-za-slovo). Не снимайте без необходимости проверки ревью/защиту.

Настройки не были изменены агентом: GitHub API из среды вернул Forbidden. Доступ по Git позволяет отправить workflow, но не доказывает доступ к административным настройкам API.

## Первый запуск

1. Откройте Actions → **Deploy Slovo za Slovo to GitHub Pages**.
2. Нажмите Run workflow; выберите проверенную ветку, например feat/slovo-za-slovo.
3. Запустите workflow. При настроенном одобрении environment подтвердите deploy в GitHub.
4. После успеха откройте URL из задачи Publish selected version / environment github-pages.

Ожидаемый стандартный адрес — `https://ElenaIlyina.github.io/rus-flash/`, если репозиторий не переименован и собственный домен не настроен. До успешного запуска адрес не считается опубликованным. Не открывайте _site по file://: клиент требует HTTP.

## Проверки

- Локально выполнены та же сборка и проверка статического артефакта.
- Браузерный тест проверяет работу под префиксом /rus-flash/, а не только в корне сервера: главная, карточка, дашборд, ссылки назад.
- Проверка артефакта подтверждает наличие файлов, не достоверность учебных ответов.
- Успешный локальный тест не подтверждает успешный workflow GitHub: нужны настоящий запуск и его URL.

## Ограничения и обновления

История остаётся в localStorage посетителя. Новый публичный origin не наследует прогресс localhost, другого порта или другого домена. Экспорт и ручной импорт JSON доступны; серверной синхронизации пока нет. Не очищайте старое хранилище в расчёте на автоматический перенос.

Демонстрационные навыки/проценты остаются явно помеченными. Pages не добавляет RAG, проверенность контента, PWA или сервер. Перед использованием школьниками нужен проверенный модуль по спецификации качества.

После следующих изменений снова запустите workflow вручную. Для возврата прежней версии выберите сохранённую ветку/тег с совместимым workflow и сборкой, затем выполните ручную публикацию. Сохранённые SHA actions обновляются отдельным проверяемым изменением.

## Ошибка защиты ветки

Если main публикуется, а feat/slovo-za-slovo отклоняется с «not allowed to deploy
to github-pages due to environment protection rules», сборка не является
причиной. В Settings → Environments → github-pages → Deployment branches and tags
выберите Selected branches and tags и разрешите main и конкретную рабочую
ветку. Остальные проверки защиты сохраняются. После сохранения повторите
workflow выбранной ветки. Изменение workflow не обходит эту настройку.
