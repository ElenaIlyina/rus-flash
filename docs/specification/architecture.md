## Реализованная версия

Статическое приложение: HTML, CSS, JavaScript ES modules; сборка данных — Python
standard library. Node/npm и сервер приложения не нужны. Для fetch необходим
статический HTTP-сервер. Исходные карточки хранятся в data/, браузер читает
сгенерированные копии из html/assets/data/.

| Компонент | Фактическое поведение | Источник |
|---|---|---|
| Сборка | JSON-исходники → каталог и отдельные JSON карточек | scripts/install.sh, scripts/build_app_data.py |
| Оболочка | Одна HTML-страница, шапка, меню, основной блок, диалог | html/index.html |
| Навигация и экраны | Hash-маршруты, замена основного содержимого без перезагрузки | html/js/app.js |

| Загрузка и адаптер | Ленивая загрузка карточки; bitmask → multiple_choice, остальные → short_text | html/js/data.js |

## Контракт навигации

| Адрес после # | Экран |
|---|---|
| study или пустой адрес | Главная, реальные счётчики и демонстрационная полоса статусов |
| bank | Поиск и фильтры банка |
| bank?topic=0…3 | Банк одного из четырёх направлений |
| card/0ABFEC | Карточка по ID |
| progress | Демонстрационный дашборд |
| progress?view=preview | Тот же демо-дашборд; scenario, topic, due управляют примером |
| progress?view=history | Реальная история и показатели попыток |
| knowledge | Заготовка справочника |
| knowledge?card=0ABFEC | Заготовка связанных правил с возвратом к карточке |

`route()` разбирает location.hash, обработчик hashchange вызывает render().
Назад/вперёд работают через историю браузера. При переходе сбрасывается число
порций банка на первую; точная позиция прокрутки не восстанавливается.
Фильтры в текущей сессии страницы хранятся в переменной, а не в адресе.
Старые входы `?id=…` и `?task=…` переводятся в hash-маршрут.
Отдельных bank.html/card.html нет; ссылки «Перейти к содержимому» тоже нет.

## Реальные данные и демонстрация

Событие попытки содержит UUID, cardId, ISO-время, correct, assisted,
materialVersion=1. Совпадение с исходным ответом не означает редакторскую
проверку. Повторная отправка в рамках открытой карточки и ответ после разбора
отмечаются assisted. Перезагрузка начинает новый сеанс карточки: строгий
контракт учебных назначений ещё не реализован.

Реальная история считает уникальные карточки с попытками, долю совпадений
среди самостоятельных отправок и ручные отметки studied. Это не оценка навыков.
Демо навыков содержит 24 навыка: закрепление 9/24 (38%), охват 17/24 (71%).
Полоса на главной — отдельная фикстура статусов карточек, масштабированная
к размеру каталога. Она не выводится из действий пользователя.

Экспорт и импорт доступны на обоих представлениях прогресса и всегда работают
с реальной историей. Файл читается локально, предварительно проверяется,
затем объединяется по явному подтверждению. При ошибке записи восстанавливаются
предыдущие значения. Это не транзакция между вкладками и не серверная
синхронизация. [Полный контракт](progress-transfer.md).

## Сборка, файлы и проверки

Сборка создаёт только данные действующего UI. Классификатор из generate_manifest.py
используется build_app_data.py; отдельный запуск старого манифеста сохранён для
служебной утилиты verify_answers_fipi.py, а не для сайта.
Удалены legacy.html, dashboard.html, stats.html, ezhik.png и генераторы старого HTML.
История вариантов дизайна остаётся в Git и [архиве](../design-directions.md).

Пять действующих браузерных наборов проверяют интерфейс, главную, демо,
перенос прогресса и пути GitHub Pages. Проверка артефакта контролирует файлы,
импорты CSS/JS и комплектность карточек. Команды — в [руководстве ревью](../interface-review.md).
Они не подтверждают предметную достоверность материалов или эффективность обучения.

## Предлагаемая целевая декомпозиция

**ARC-01 · Предлагается.** Небольшие независимые модули, без обязательного UI-фреймворка:

1. Content repository: версия карточек, текстов, правил, схем и review.
2. Assessment engine: response + версия политики → result/reason; без DOM и сетевых запросов.
3. Learning reducer: история + профиль + now → состояние навыков и основания.
4. Route planner: состояние, редакторский граф и доступный контент → следующая рекомендация с причиной.
5. Progress projection: модуль и проекции → числители, знаменатели, четыре сегмента.
6. UI: отображает результаты модулей, не прячет учебные пороги в CSS/обработчиках кнопок.
7. Persistence: локальное хранение; затем необязательный адаптер синхронизации.
8. Editorial pipeline: импорт, валидация, RAG-черновики, проверка человеком, выпуск статического контента.

**ARC-02 · Согласовано.** RAG — инструмент подготовки. Клиент не содержит модельных секретов и не выдаёт непроверенную генерацию за учебное объяснение. Приложение работает без модели и обязательного аккаунта.

**ARC-03 · Предлагается.** Чистые вычислительные функции получают now и версии явными аргументами. Не читают Date.now/random/network внутри редьюсера. Одинаковые входы дают одинаковые статусы и рекомендации. Это позволяет сравнить алгоритмы и воспроизвести научный эксперимент.

**ARC-04 · Предлагается.** История событий — источник, проекции пересчитываются. Новая модель вводится миграцией с резервным экспортом и отчётом. Старые события correct без проверенной версии материала не превращаются в доказанное освоение.

**ARC-05 · Согласовано.** Офлайн и PWA, экспорт/импорт и синхронизация — разные возможности. Доступны экспорт и локальный импорт JSON с подтверждением; наличие локального хранилища само по себе не означает офлайн-загрузку всего банка. Контракты сервера и разрешение конфликтов остаются открытыми.

**ARC-06 · Предлагается.** После выбора дизайна переносить представление поверх общей модели; не плодить отдельную учебную логику для трёх визуальных направлений.
